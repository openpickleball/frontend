Decision proposal · Frontend

OpenPB frontend stack

React Native, SvelteKit or Flutter for the player-facing app: what each one costs us now, what each one makes possible later, and which one to start with.

Status Decided Date 17 Nov 2026 Scope Web app first, mobile later
Recommendation

Build a responsive web app in SvelteKit, ship it as an installable PWA, and keep the data layer in plain TypeScript so a mobile app can reuse it later.

Most of what OpenPB does is pages people open from a link: a player profile, a rating history, a club leaderboard, a score to enter after a game. That work is what the web is best at, and SvelteKit is the fastest and simplest way to do it of the three options. If we later need to be in the app stores, we can wrap the same app with Capacitor for very little effort. If we eventually want a fully native app, we can build it in Expo and reuse our TypeScript API client and domain logic. Flutter is the weakest fit because its web output is the part we need most and the part it does worst.

Context

What we're building

Your read is right: most of the app is reading data and entering it, and the heavy logic (rating calculation, match validation) belongs on the server, where it can be published and audited. The screens we can foresee:

  • Read: player profiles, rating history charts, match lists, club and event leaderboards, player search.
  • Write: sign up and claim a profile, enter a match score, confirm or dispute a score someone else entered, manage a club or event.

A few needs aren't obvious from "display plus entry", and they affect the choice:

Shareable public pages

Players will paste profile and leaderboard links into group chats. Those links need server-rendered HTML so that previews show a name and rating, and so that search engines can index them. This favors a real web framework.

Score entry at the court

Scores get entered on a phone, often with weak signal. Entry should be quick, work one-handed, and queue the submission when offline. A PWA with a small sync queue covers this. We don't need a native app for it.

Older, non-technical players

Large text, real form controls, screen reader support and the browser's own zoom matter. Native HTML gives us all of these for free. A canvas renderer does not.

Live event days

Tournament brackets and leaderboards may update while people watch. That calls for websockets or server-sent events, which all three options handle. It doesn't change the decision.

Framing

These aren't three versions of the same thing

The options start from different places, and that matters more than any feature list:

  • SvelteKit is a web framework. It reaches mobile through the browser (PWA) or through a native wrapper (Capacitor).
  • React Native is a mobile framework. In practice that means Expo, which can also target the web through React Native Web. The web output works, but it's a translation layer: you write <View> and <Text>, not HTML.
  • Flutter is a mobile framework that draws every pixel itself. On the web it paints to a canvas with a WebAssembly engine, so the page isn't really HTML.

So the real question is which platform we want to be excellent on first, and how much the second platform costs. Since we're starting with web, a web-native framework has the advantage, as long as the path to mobile stays open.

Options

Each option in detail

SvelteKit

Recommended
Strengths
  • Compiles to small bundles with little runtime, so pages load fast on cheap phones and slow connections.
  • Server rendering, form actions and data loading are built in. Forms work before JavaScript loads and get better once it does.
  • Writing it feels like writing HTML and CSS. New contributors can read a component on day one.
  • Real HTML means accessibility, autofill, zoom and link previews work without extra effort.
  • Installable PWA with offline support and push notifications, including on iPhone from the home screen.
Weaknesses
  • A smaller community than React: fewer ready-made components and fewer developers who already know it.
  • Svelte 5's runes changed how components are written, so some older tutorials and libraries are out of date.
  • No direct route to a truly native app. Mobile means a PWA, a Capacitor wrapper, or a second app in another framework.
  • AI coding tools are somewhat better at React than at Svelte 5, though the gap has narrowed.

Adding mobile later: the PWA is free from the start. A Capacitor wrapper puts the same code in the App Store and Play Store, typically in days to a couple of weeks, with native plugins for push, camera and sharing. A fully native app would be a new Expo codebase that reuses our TypeScript API client, validation and domain types but not our UI.

React Native with Expo

Strong for mobile-first
Strengths
  • One codebase for iOS, Android and web, with truly native screens on phones.
  • Expo has removed most of the old pain: managed builds (EAS), over-the-air updates, file-based routing and a good set of native modules.
  • The largest pool of developers and contributors of the three, since most frontend developers know React.
  • The best choice if a polished native app is required within the first year.
Weaknesses
  • The web build goes through React Native Web. It works, but it isn't idiomatic HTML: most React web libraries won't run, and styling uses React Native's subset of CSS.
  • Server rendering and SEO on the web are weaker than in a web framework, and they're the newest, least proven part of Expo.
  • Mobile overhead starts on day one: simulators, device testing, native builds, SDK upgrades and store releases.
  • Web pages carry more JavaScript than SvelteKit pages, which shows on slow phones.

Adding mobile later: already done. That's the point of choosing it. The cost is paying for mobile from the start even while we ship web only.

Flutter

Not recommended
Strengths
  • Excellent mobile apps that look the same everywhere, with great hot reload and tooling.
  • Dart is pleasant and strongly typed, and the built-in widget set is large and consistent.
  • Strong for apps with lots of custom animation or drawing.
Weaknesses
  • On the web it draws to a canvas, so the first load is large (often several megabytes) and slow on mobile data.
  • Pages aren't real HTML. Search engines and link previews see very little, and text selection, browser find and autofill behave differently.
  • Screen reader support on the web relies on a separate semantics layer, which is harder to get right for older players.
  • Dart sits outside the JavaScript ecosystem, so we can't share code with a TypeScript backend or tooling, and fewer web developers can contribute.

Adding mobile later: easy, since mobile is Flutter's home. But we'd be accepting a weak version of the web app, which is the part we're building first.

One alternative worth naming: React for the web (Next.js or React Router) with an Expo app later. You get React's contributor pool and could share hooks and logic with a future native app, at the cost of a heavier, more complex web stack than SvelteKit. If a large contributor pool turns out to matter more than speed and simplicity, this is the runner-up.

Mobile

The path to mobile, one step at a time

You're right to worry about mobile overhead. Each step below adds cost, and we only take the next one when there's a clear reason. Steps 1 to 3 all use the same SvelteKit code.

  1. Responsive web app Designed for phones first, since that's where most scores get entered. Cost: none beyond the web app
  2. Installable PWA Home screen icon, full-screen view, offline score queue, push notifications ("your rating changed"). On iPhone, push only works once the app is added to the home screen. Cost: a manifest, a service worker, a few days
  3. Store listing with Capacitor The same web app in a native shell, for people who look for apps in the store, plus native push, sharing and camera plugins. Cost: Apple developer program ($99/yr), Google Play ($25 once), store review, a device test pass per release
  4. Native app in Expo Only if the wrapped app feels limiting: widgets, background work, heavy offline use, or a UI that has to feel fully native. Cost: a second UI codebase that shares our TypeScript data layer

Store overhead to plan for: Apple reviews every release, usually within a day or two but sometimes with rejections to fix. New personal Google Play accounts must run a closed test with at least 12 testers for 14 days before going public. An organization account avoids that, so register OpenPB as an organization when the time comes.

Keeping options open

Choices that make the later steps cheap

Mobile code reuse depends less on the UI framework and more on how we structure the code from the start:

  • API first. The backend publishes an OpenAPI spec, and we generate a typed TypeScript client from it. Every frontend, current or future, talks to the same contract.
  • A shared core package. Domain types, validation schemas (for example Zod or Valibot), score formatting and the offline submission queue live in plain TypeScript with no Svelte imports. An Expo app could use it unchanged.
  • Thin components. Svelte components handle display and input. Rules such as "a game to 11, win by 2" live in the core package, not in a component.
  • Design tokens as data. Colors, type scale and spacing are defined once (we already have the @theme block from the site) so a native app can reuse them.
  • Auth that works outside a browser. Choose an auth approach that supports both cookies for the web and tokens for a native app, so adding mobile doesn't mean redoing login.
Revisit

When we'd reconsider

This decision is about how we start, not a permanent commitment. We'd revisit it if:

  • Partners or clubs require a native app in the stores sooner than a Capacitor wrapper can deliver one.
  • We need native features a wrapper handles poorly: home screen widgets, background location, or Apple Watch scoring.
  • We can't find enough Svelte contributors, and the lack of React is the reason.
  • Usage data shows most players stay on mobile and the share links aren't driving traffic.
Open questions

What would change this recommendation

  1. Is there a date by which we must be in the App Store or Play Store? If it's within six months of launch, Expo becomes more attractive.
  2. Who is writing the frontend: one or two core developers, or a wider volunteer community? A wider community favors React.
  3. What is the backend written in? If it's TypeScript, we can share more code between server and client.
  4. Do we expect any feature that needs the phone itself, such as Bluetooth scoring devices or court check-in by location?
Scores and weights are judgment calls meant to start a discussion. Prices and store rules are as of November 2026 and should be checked before we register accounts.
